# SQL Server: от пустого sibling до двух закрытых планов

Руководство по проверенному проходу 11–12 октября 2026 года: адаптация SQL Server
2019 / Northwind, затем `dbo.GetReorderCandidates`. Обычный процесс описан в
[контракте sibling](../README.md), текущий SQL harness — в [README](../../README.md).
Здесь собраны входы человека, порядок команд и наблюдаемые условия завершения.

Это процедура для **нового пустого sibling** и отдельно подготовленной dev-базы.
В уже завершённом проекте повторять reset, init и исторические proof-команды не нужно.
Текущий parser принимает девять тестов; один canary относится к состоянию первого плана.
Руководство подготовлено после принятого прохода как отдельная документация:
его сохранение не является новым native docs-closeout или release qualification.

## 1. Предпосылки и обозначения

Нужны подготовленные macOS, Git, zsh, rg, авторизованный Codex CLI и доверенный
физический checkout Planveyor. В проходе использован source commit
`8c5256e752cedafb4aa3c06cec97bef29d74f947`; runtime в ходе работы не изменялся.
Повтор на другой версии требует проверки её собственного контракта.

| Компонент | Фактически использованная версия / контракт |
| --- | --- |
| macOS | 27.0.1; другие ОС этим проходом не проверены |
| Python / Copier / PyYAML | 3.12.14 / 9.18.2 / 6.0.3 |
| .NET SDK | 10.0.401; в проекте `rollForward: latestFeature` |
| go-sqlcmd / Codex CLI | 1.10.0 / 0.162.0 |
| SqlPackage | 170.5.96, локальный dotnet tool |
| Microsoft.Build.Sql | 2.3.0, Sql150DatabaseSchemaProvider |
| tSQLt.Dacpacs | 1.0.8083.3529, DacpacName tSQLt.2019 |
| SQLFluff | 3.4.2, tsql/raw, длина 120 |
| Native Manager и роли | `gpt-6.1-sol`, effort `ultra` |

SQL Server 2019 с compatibility 150, источник схемы Northwind, отдельную dev-базу,
рабочий логин и database-level маркер `planveyor.designated_dev` предоставляет
администратор. В dev-базе логину разрешена работа harness; в Northwind — только
чтение схемы. Логин не sysadmin. Роли не создают сервер, логины, CLR и маркер.

Внешние предпосылки, отсутствующие в публичном sibling:

- проверенный комплект стенда с `setup.sh`, `db-state.sh` и проверяемым `vendor/`;
- заранее подготовленный защищённый файл подключения;
- согласованный комплект проектных настроек моделей: `config.toml` и восемь
  `agents/*.toml`, всего девять файлов. Он задаёт главную сессию и восемь agent
  entries; имя роли не доказывает фактическую модель.

Без этих предпосылок остановитесь и получите их у владельца. Этот документ
не содержит замену административному harness или установщик окружения.

Далее значения в угловых скобках — placeholders. Владелец подставляет свои пути
и identity локально; их не сохраняют в публичные планы, правила или отчёты.

```sh
PY312_BIN='<каталог bin подготовленного Python 3.12>'
PLANVEYOR_RUNTIME_ROOT='<физический доверенный checkout Planveyor>'
PASS_DIR='<новый каталог прохода>'
STAND_DIR='<предоставленный администратором комплект стенда>'
SIBLING_DIR="$PASS_DIR/planveyor-mssql"
```

Каждую показанную ниже команду `planveyor` выполняйте с этим префиксом:

```sh
env -u PLANVEYOR_CODEX_HOME \
  PATH="$PY312_BIN:$PLANVEYOR_RUNTIME_ROOT/bin:$PATH" planveyor sibling plan
```

Далее префикс опущен только для читаемости; `sibling plan` заменяется нужными
аргументами. Это выбор окружения одного процесса, без изменения shell config
или установки нового runtime. Роли этого прохода использовали обычный Codex home.
Не подменяйте его отдельным home при повторении.

До первой команды в каждом рабочем чате проверьте подготовленные версии:

```sh
"$PY312_BIN/python3" --version
"$PY312_BIN/python3" -m copier --version
dotnet --list-sdks
sqlcmd --version
codex --version
codex login status
git -C "$TMPDIR" rev-parse --is-inside-work-tree
```

`TMPDIR` должен существовать вне любого Git-репозитория: последний вызов должен
отказать именно потому, что каталог не является репозиторием. Отсутствующий
каталог не засчитывается. Эти проверки ничего не устанавливают.

## 2. Подготовка стенда и создание sibling

Работает один оператор. Сначала откройте обычный чат в `PASS_DIR`, после init —
рабочий чат в `SIBLING_DIR`. Координатор, если есть, наблюдает за журналом и
не становится вторым исполнителем. До запуска заведите обычный каталог `journal/`
в каталоге прохода; после init используйте также ignored `.tmp/journal/` sibling.

Reset выполняется только после прямого разрешения владельца на **весь** объём:
проверку vendor, tSQLt PrepareServer (CLR и ключ подписи), пересоздание выделенной
пустой dev-базы, логина/прав/маркера, загрузку Northwind со схемой и демо-данными,
временный tSQLt smoke и удаление smoke-базы, запись результата подготовки.
Это отдельная административная подготовка, не действие SQL-ролей.

```sh
"$STAND_DIR/setup.sh" --reset-dev
"$STAND_DIR/db-state.sh"
```

В принятом проходе первый скрипт дал rc 0 и `RESULT: OK`. Второй дал rc 1:
dev-база не содержала пользовательских объектов и тестовых классов, маркер
присутствовал, но заключительное чтение отсутствующей `tSQLt.TestResult` отказало.
Допустим только этот диагностированный случай пустой базы. Ошибку подключения,
прав или неполный вывод нельзя объявлять ожидаемой. Значение маркера не является
критерием: проверяется наличие. Непустая или чужая база — остановка.

Создайте sibling с явно выбранной Git identity:

```sh
planveyor sibling init "$SIBLING_DIR" \
  --author-name '<ваше имя>' --author-email '<ваш email>'
```

Ожидаются rc 0, `Git identity: …`, `Sibling создан: …`, пройденный contract check
и один начальный коммит. Проверки из каталога прохода:

```sh
git -C "$SIBLING_DIR" rev-list --count HEAD
git -C "$SIBLING_DIR" status --short
```

Затем владелец разрешает копирование заранее подготовленного файла подключения
в новый sibling. Оператор переносит его без перезаписи существующего файла и
без вывода значений: `.env.local` должен быть regular file без symlink, mode 0600.
Нужны ключи SQLCMDSERVER, SQLCMDDBNAME, SQLCMDUSER, SQLCMDPASSWORD; значения читает
только обвязка, не роли. После согласованного копирования:

```sh
git -C "$SIBLING_DIR" check-ignore .env.local
git -C "$SIBLING_DIR" ls-files .env.local
```

Первая команда подтверждает ignored, вторая ничего не выводит. Не исполняйте
`.env.local` через `source`. Публичного примера значений здесь нет.

Установите предоставленный владельцем комплект моделей в новую `.codex/`
sibling без перезаписи существующих файлов. Проверьте совпадение копий по SHA-256
и добавьте `.codex/` в локальный `.git/info/exclude`. Общий Codex config не меняется.
При первом `architect` и `run` сверяйте фактические model/effort Manager и ролей
по runtime metadata. В проходе это были Sol 6.1 / Ultra. Если конфигурация не
применена, остановитесь; trust-настройки меняет владелец, не обходной скрипт.

Песочница чата определяется при его открытии: один `cd` не расширяет доступ.
Native `architect`/`run` могут требовать доступа к обычному хранилищу сессий Codex;
init/commit и локальная конфигурация — к защищённым каталогам. Повтор с повышенным
доступом допустим для конкретно доказанного отказа доступа и в уже разрешённом
объёме. Не называйте любой rc 3 отказом песочницы.

## 3. Первый план: адаптация стека

Откройте sibling в обычном рабочем чате. Все дальнейшие shell-команды, кроме
явно указанных проверок из родительского каталога, выполняются из корня sibling.
Доставленный навык находится в
`.agents/skills/`; при отсутствии навыка проверьте корень чата. Глобальная копия,
symlink и новый plugin не нужны.

Вставьте запрос в чат; это **сообщение навыку**, а не shell-команда:

```text
$planveyor-plan-draft Создай и сделай текущим план адаптации sibling под мой стек по docs/_template_stack_brief.md. Создай docs/stack_brief.md как вход плана. Задай вопросы по неподтверждённым решениям. Следующую полезную задачу согласуем отдельно.

Факты о моём стеке:
```

К этому же сообщению добавьте следующий блок, предварительно сверив его с
действительно подготовленным стендом. Это исходные факты, а не готовая анкета:

## 4. Run, независимые проверки и первый коммит

```sh
planveyor sibling run
```

Следуйте напечатанному следующему шагу. Вопросы ролей друг другу с `needs_owner=no`
решают сами роли. Лимит хода Manager позволяет повторить тот же `run`; ошибка
или незнакомый отказ требуют разбора, а не слепого повторения. Уже работающую
команду не запускают второй раз и не прерывают ради проверки прогресса.

Роли используют следующий harness. Это команды, ожидаемые в их Evidence;
оператор не запускает параллельную SQL-проверку во время `run`:

```sh
make setup
make db-extract
make db-build
make lint
make test
make check-secrets
make db-proof JUNIT="docs/code_reviews/assets/<новый-plan-stem>/canary.junit.xml"
```

`setup` и Extract выполняет Coder. Reviewer самостоятельно повторяет необходимые
офлайн-проверки, затем выполняет собственный полный proof:

```sh
make db-proof JUNIT="docs/code_reviews/assets/<новый-plan-stem>/canary.review.junit.xml"
make db-state
```

Уголковые placeholders в этих примерах заменяются literal относительными путями
до выполнения. Извлечение даёт 36 файлов схемы: 13 таблиц, 16 представлений,
7 процедур. Каждый live proof выполняет build → свежий guard → Publish → RunAll
→ неизменённый formatter → атомарный очищенный XML. Coder и Reviewer работают
последовательно с одной dev-базой. В обоих JUnit первого плана ожидается
**1 testcase, 0 failures, 0 errors, 0 skipped**: постоянный canary реальной Products.

В Evidence нужны точная команда, отдельные make/wrapper rc, HEAD и canonical
bundle snapshot до/после proof, путь и SHA-256 XML, счётчики и имена testcase.
Одинаковые XML hash сами по себе не доказывают независимость: нужны отдельные
фактические прогоны. `db-state` — contextual readback, не замена JUnit.

После Reviewer и приёмки Architect получите preview:

```sh
planveyor sibling close
```

Прочитайте **весь** набор файлов и сообщение коммита. Разрешение владельца Ф3,
предусмотренное сценарием, относится к каждому проверенному preview:

```text
Разрешаю локальные коммиты этого прохода: каждый planveyor sibling close --commit после close с прочитанным набором. Push и публикацию не разрешаю.
```

Текст разрешения пишет человек; наличие его примера в руководстве не является
разрешением. При уже данном Ф3 повторное общее согласование не нужно. После
изменения набора сначала получите новый preview. Затем:

```sh
planveyor sibling close --commit
```

Ожидаются rc 0, локальный коммит и `Done`. Проверьте фактические hash, файлы и
сообщение относительно preview. Green review, подготовка и `Done` сами по себе
не разрешают push или публикацию.

## 5. Документы и ready — после каждого плана

После semantic commit выполните отдельно:

```sh
planveyor sibling run
planveyor sibling close
```

Команды исполняются по одной: дождитесь завершения `run`, прочитайте его вывод,
затем `close`. Если `close` показывает отдельный docs-коммит, прочитайте новый
набор и сообщение и примените разрешённый Ф3 через `close --commit`. Если docs
closeout дал `final_docs_commit=no_op`, дополнительный коммит не нужен.

Этап закрыт только после rc 0 и фразы:

```text
План и документы закрыты. Можно начать следующую задачу.
```

Теперь:

```sh
planveyor sibling ready
```

Требуются rc 0 **и** точный итог:

```text
Consumer contract и выбранный план закрыты. Готовность отдельного release или SQL не проверялась.
```

Другой текст с rc 0 может означать незавершённую задачу: выполните указанный
следующий шаг. `ready` не повторяет SQL и не даёт release readiness. До перехода
к следующему плану отдельно проверьте актуальные собственные JUnit обеих ролей.

## 6. Второй план: товары к дозаказу

Только после полного закрытия адаптации отправьте в чат этот прямой запрос:

```text
$planveyor-plan-draft Создай и сделай текущим обычный план по моему прямому поручению: Реализовать читающую процедуру dbo.GetReorderCandidates без параметров. Она возвращает товары только с Discontinued = 0 и Shortage = ReorderLevel - (UnitsInStock + UnitsOnOrder) > 0. Числовые NULL считаются 0, значения приводятся к int до арифметики. Колонки: ProductID int, ProductName nvarchar(40), Shortage int, сортировка по ProductID. Восемь содержательных бизнес-тестов tSQLt (T1–T8) и постоянный canary dbo.Products проходят в самостоятельных прогонах Coder и Reviewer в принятой dev-среде: девять testcase, ноль failures, errors и skipped. Покажи matching open follow-up, сохрани его неизменным и добавь source_ref#item_id в Context links.
```

Навык выполняет bounded discovery. Matching open follow-up сохраняется без
изменений; его `source_ref#item_id` добавляется как контекст. Если совпадения нет,
фиксируется отсутствие совпадения без искусственной row. В принятом проходе
совпадений не было. Новый план выбирается по фактически созданному пути:

```sh
planveyor sibling plan "docs/plans/<фактически-созданный-план>.md"
planveyor sibling architect
```

После чтения постановки передайте фактический ответ. Ниже точный публичный
текст входа принятого второго плана: О20 и техническое уточнение Т. В том проходе
вопрос имел id Q1; при повторе используйте id из текущего вывода.

```text
Отвечаю по поручению Owner. Подтверждаю раздел «Как я понял задачу»: читающая процедура dbo.GetReorderCandidates без параметров; только Discontinued = 0 и Shortage = ReorderLevel - (UnitsInStock + UnitsOnOrder) > 0; числовые NULL = 0; приведение к int до арифметики; колонки ProductID int, ProductName nvarchar(40), Shortage int; сортировка по ProductID. Восемь бизнес-тестов:
T1 — пустая Products, пустой результат;
T2 — активный товар 10/4/2, Shortage 4;
T3 — нулевой и отрицательный дефицит не попадают;
T4 — дефицит, покрытый заказами в пути, не попадает;
T5 — снятый с продажи товар с дефицитом исключён;
T6 — NULL в каждом числовом поле и их сочетаниях; NULL порога не создаёт кандидата;
T7 — ReorderLevel 32767 и оба остатка 32767 — без переполнения;

Девятый — постоянный canary. Coder и Reviewer — самостоятельные последовательные прогоны, каждый со своим JUnit: девять testcase, ноль failures, errors и skipped. Подтверждаю переход в Architect draft. Это не разрешение на коммит.

Отвечаю по поручению Owner. Это технический вопрос обвязки, а не решение владельца: исправьте по документации инструмента и фактам стека из анкеты, не меняя Scope, права и приёмку. Если исправление требует изменить что-то из этого — верните вопрос с вариантами.
```

```sh
planveyor sibling answer Q1 < ".tmp/journal/answers/<новый-план>-Q1.txt"
planveyor sibling architect
planveyor sibling run
```

Каждый следующий вызов допустим после результата предыдущего. В принятом проходе
`answer` направил к Architect; тот закрыл Q1, затем направил к `run`. Ограниченная
адаптация существующих parser/proof, офлайн-тестов, README и локальных правил
под девять тестов входила в уже согласованную приёмку.

Coder и Reviewer получают каждый свой полный proof на одном актуальном bundle:

```sh
make db-proof JUNIT="docs/code_reviews/assets/<новый-plan-stem>/reorder.junit.xml"
make db-proof JUNIT="docs/code_reviews/assets/<новый-plan-stem>/reorder.review.junit.xml"
```

Это **два разных последовательных запуска разных ролей**, не общий запуск
оператора. Каждый XML содержит точные T1–T8 и постоянный canary: **9/0/0/0**.
T6 покрывает NULL каждого числового поля и сочетания; T8 проверяет метаданные
самой процедуры и сортировку. Одних totals без девяти уникальных identities
недостаточно. Изменение target bytes требует обновлённого proof.

После принятия повторите разделы 4–5: `close`, прочитанный preview, разрешённый
`close --commit`, отдельный docs `run`, `close`, затем `ready` с точной фразой.
Не передавайте tracked исторический XML в JUNIT: harness отвергает такой путь
до удаления, сборки и SQL. Для новой задачи нужен новый фактический plan-stem.

## 7. Отказы и границы повторения

Записывайте команду, вход, время начала/конца, cwd, очищенные stdout/stderr и rc.
В журнале различайте код `make` и код обвязки:

| Wrapper rc | Смысл |
| --- | --- |
| 0 | Успех |
| 1 | Test/JUnit failure или malformed report |
| 2 | Configuration/path/Git/secrets/invalid Extract input |
| 3 | Цель dev не прошла проверку; Publish не выполняется |
| 4 | Connection/read SQL failure |
| 5 | Build/lint/Extract artifact или atomic exchange failure |
| 6 | Publish failure |

Останавливайтесь при неподтверждённой предпосылке, неизвестном нетехническом
вопросе, несовпадении модели, чужих объектах/лишних тестах или необходимости
изменить Scope, права и приёмку. Нештатное поведение facade и третий одинаковый
технический возврат передаются владельцу с командой, выводом и вариантами.
В сценарии контрольные точки времени — 9 часов от init для адаптации и 8 часов
от запроса второй задачи; это повод доложить владельцу и получить решение,
а не срок автоматического kill/restart и не обещание длительности.

Не исправляйте runtime, terminal plan/review, receipts, counts, guards или
настройки среды ради зелёного результата. Технические findings проходят обычные
роли. Существующие ограничения описаны также в [README](../../README.md):
свежий target guard, строгий XML, redaction, Git/JUNIT boundary и отсутствие
автоматических SQL retries сохраняются.
