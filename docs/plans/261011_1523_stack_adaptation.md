## Solution (high level)
1. Все проектные действия идут через объявленные цели `Makefile` и единственную обвязку `scripts/sql.py` на стандартной библиотеке Python. Обвязка читает локальную конфигурацию, проверяет предпосылки и возвращает категории отказа 0–6; роли не читают значения credentials и не обходят обвязку прямым SQL.
2. Схема-источник `Northwind` и dev-цель разделены: `db-extract` только читает источник, `db-proof` записывает только в отдельную назначенную dev-базу. Extract создаёт временный набор, удаляет каталоги безопасности, проверяет запрещённый остаточный SQL и количество 13/16/7; только полный допустимый набор атомарно заменяет `sql/Northwind/Imported/`. Имена объектов не разбираются, одночастные имена сохраняются.
3. Основной SQL-проект объединяет `Imported/` и `Authored/` для `Sql150DatabaseSchemaProvider`; тестовый проект ссылается на основной и `tSQLt.Dacpacs` с `DacpacName=tSQLt.2019`. Единственный постоянный тест проверяет реальную `dbo.Products` типа `U`, без `FakeTable`/`NewTestClass` и без чтения бизнес-данных. Версии и флаги сохраняют точные значения Owner.
4. Один `db-proof` сначала проверяет допустимость `JUNIT`/ответ Git, удаляет только старый достоверно untracked XML и собирает проекты; непосредственно перед Publish свежим запросом проверяет dev-цель. Затем та же цель проходит Publish → `tSQLt.RunAll` → `tSQLt.XmlResultFormatter`; текущий очищенный JUnit строго разбирается и атомарно записывается. Отказ любой стадии не становится зелёным из-за старого XML или сообщения об успехе.
5. Coder выполняет первоначальный setup/Extract и свой proof; Reviewer последовательно проверяет те же исходники офлайн и отдельным живым proof с другим JUnit. `db-state` — самостоятельная читающая contextual lane Architect/Reviewer, не замена proof. Зависимости и кэши остаются в `.tmp/`, а JUnit — durable evidence в `docs/code_reviews/assets/`.
6. Постоянные ограничения и команды Coder переносит в корневой `README.md` и только локальные секции восьми carriers; общие process bodies не меняются. Planner в своей стадии фиксирует exact targets, manifests, code draft и regression inventory. Architect принимает актуальный review, после чего human `sibling close` показывает проверенный набор; только отдельное разрешение на `close --commit` открывает commit. Следующая бизнес-задача не активируется автоматически.

Dev-база подготовлена администратором; роли подтверждают цель через обвязку.
Значения .env.local читает только обвязка. В документах нет секретов, серверов и private machine paths.
Зависимости ставит make setup один раз в .tmp; системные инструменты и окружение не менять.
`PYBIN` относится к движку Planveyor; проект использует объявленный Python 3.12 из `PATH` за целями `make`. Путь интерпретатора движка в проект не переносится.
Серверная подготовка и минимальные права остаются у администратора; при недостающей предпосылке роль фиксирует отказ, а не включает CLR, не меняет права и не пересоздаёт среду.
Общая dev-база и Imported требуют последовательных действий. Reviewer повторяет proof на тех же проверяемых исходниках после Coder; прежний отчёт не переиспользуется как новый прогон.
Граница authority перед записью уточнений: `decision lifecycle` — согласованная постановка из фактов Owner, исполнение ещё не принято; `canonical writable owner` постановки — Architect в этом плане, кода проверок — Coder в `scripts/sql.py`. Downstream enforcement — обвязка, proof — офлайн-тесты и независимые JUnit, derived consumer — журналы и `make db-state`. Текст плана, prompt и сообщение об успехе не заменяют эти carriers.
Граница нового admission carrier: `decision lifecycle` — Architect-owned N/A решение по отсутствию нового machine authority Planveyor; `canonical writable owner` — Architect, ровно один `plan_meta.machine_authority_decision` в этом плане. Downstream enforcement/readback — existing `plan_lint.py`/`plan_status_oracle.py`; Planner пишет только derived `code_draft_meta.machine_authority_decision_ref`. SQL-вводные не становятся machine-authority confirmation, а локальная проверка dev-цели/JUNIT остаётся кодом Coder и не меняет reader/admission/routing/writer contract движка.

## Risks / Open questions (summary)
Неверная SQL-цель, частичный Extract, обрезанный/невалидный JUnit, устаревший XML, секреты при ошибках.
Риски закрывают обвязка и офлайн-тесты; живую готовность — независимые proof.
Сверка постановки не обнаружила новых решений Owner или расширения scope. Наличие SQL-проектов, зависимостей, прав подключения и успешных JUnit пока не доказано.
