## Problem

1. В рабочем контракте `global.json` и обвязка допускают только SDK .NET 10. Mac с SDK 11 требует ручного выбора другой установки перед командами проекта.
2. Поддержка SDK 11 требует совместимого runtime .NET 10 для закреплённого SqlPackage. Одинаковое наличие команды `dotnet` не доказывает, что инструмент запустится.
3. Точное старое требование к SDK повторено в восьми локальных правилах ролей и проверяется побайтно. Его нужно обновить синхронно с поведением, сохранив защиту остальных правил.

## Как я понял задачу

Добавляем стабильный SDK 11 на macOS со штатной CLI и сохраняем действующий минимум SDK 10.
Подготовленная ARM64-установка .NET выбирается в среде запуска; проект предпочитает подходящий SDK 10 и переходит на 11 при его отсутствии.
Меняются проверка SDK, `global.json`, тесты, README и только SDK-фраза восьми локальных правил; установка инструментов и изменение постоянного PATH в работу ролей не входят.
Coder готовит две независимые офлайн-строки: SDK 10 в текущем sibling и SDK 11 в отдельной Git-копии без конфигурации БД; Reviewer сверяет обе строки с итоговым снимком и независимо повторяет проверки SDK 11 в текущем sibling без setup.
Два последовательных guarded SQL-прогона и точный локальный commit требуют отдельных последующих разрешений по готовым результатам.
Owner дословно ответил на Q1 «да, подтверждаю»; постановка принята, Q1 закрыт. Точный executable draft, пути и команды подготовки принадлежат Planner; допуски на SQL и конкретный commit этим ответом не предоставлены.

## Solution (high level)

1. Задать нижнюю границу `10.0.401`, `rollForward: major` и `allowPrerelease: false` в `global.json`. Обвязка допускает только стабильные `10.0.x` от `10.0.401` и `11.0.x` от `11.0.100`. Отдельно тестировать выбор resolver и отказ обвязки для несовместимой версии.
2. Описать в README единый источник правил выбора SDK и подготовку постоянной ARM64-установки. Тот же `dotnet` должен видеть `Microsoft.NETCore.App` 10.0.x от `10.0.11` для SqlPackage. В восьми локальных правилах заменить только дублированное требование к SDK ссылкой на это правило README.
3. Во всех восьми local bodies заменить ровно одно вхождение `SDK 10.0.401/latestFeature` на `SDK — по README.md («Среда и зависимости»)`. В тестах разрешить только этот точный переход от старого `HEAD` и обычное равенство после коммита; остальные local bytes, shared prefixes и отрицательные проверки произвольных правок сохраняют прежнюю защиту. Planner задаёт точный executable draft и fixtures этого перехода.
4. Coder выполняет две отдельные подготовки и офлайн-матрицу на одном итоговом снимке: SDK 10 в текущем sibling, SDK 11 в отдельной Git-копии без `.env.local`. Их `.tmp` и физические корни различаются. Для SDK 11 используется заранее подготовленная установка, в которой resolver действительно отдаёт 11, с runtime .NET 10. Оба SQL proof позднее остаются в текущем sibling. После своего разрешённого SDK 10 proof Coder выполняет третью, отдельно объявленную подготовку кеша текущего sibling под SDK 11 и полный набор офлайн-проверок; Reviewer использует этот кеш без setup, сверяет обе исходные строки и независимо повторяет офлайн-проверки SDK 11. Порядок и границы — в блоке ниже.
5. Проверки `dotnet --version`, `dotnet --list-runtimes` и локального SqlPackage `/Version` выполняются в том же выбранном окружении до обращения к БД. Это явное операторское предусловие приёмки, а не новый runtime-guard в `Stack.tools`: его изменение в этом плане ограничено SDK-фильтром. Отказ `/Version` фиксируется собственным фактическим кодом команды и останавливает SQL-этап; код обвязки не выдумывается. После отдельного разрешения Owner выполняются два штатных `db-proof`.

## Decisions (final)

Архитектурная постановка принята фактическим ответом Owner на Q1 «да, подтверждаю». Сам Q1 не предоставлял SQL/commit authority; отдельный ограниченный SQL-допуск позднее получен как A6/CLOSED Q6 и исполняется только в его границах ниже. Конкретный commit остаётся отдельным последующим gate.

- Политика по умолчанию — подходящий SDK 10, с переходом на SDK 11 при его отсутствии. Номер `10.0.401` задаёт нижнюю границу. Конкретный патч выбирает установленный resolver.
- Матрица обычного запуска — SDK 10 и SDK 11 в одной установке выбирают 10, установка с одним SDK 11 выбирает 11. Выбор для теста SDK 11 выполняется через подготовленную отдельную установку, а байты кандидата остаются одинаковыми.
- Граница поддержки — prerelease, неподходящий minor, SDK ниже установленных порогов и будущие major дают отказ предзапусковой проверки. Нет допустимой SDK или runtime — остановка с диагностикой среды.
- Допуск к записи — только штатный guard существующего `db-proof` и отдельное разрешение Owner после офлайн-проверок. Результаты прежних SQL-прогонов остаются историческими.
- Допуск к приёмке — итоговый снимок, зелёные обе офлайн-строки и два свежих последовательных guarded proofs. Публикация — отдельное поручение Owner.
- Откат SDK-политики — возврат всего согласованного пакета файлов одним изменением при необходимости. Схема БД не меняется этим планом.
- `rollForward: major` сам по себе может выбрать следующий minor или будущий major. Верхнюю границу поддержки и отказ prerelease обеспечивает SDK-фильтр обвязки; собственный resolver, скрытый поиск другой установки и `--allow-roll-forward` для SqlPackage не добавляются.
- Подготовка установок .NET принадлежит Owner/администратору вне этого плана. Роли используют уже подготовленные установки; project-local кеши для обеих строк готовит Coder, а не Reviewer.
- Если resolver выбрал неподдерживаемый minor/major, обвязка отказывает и не перебирает другие установленные SDK. Граница поддержки не зависит от наличия рядом другой подходящей версии.
- `machine_authority_decision` имеет strict N-A `no_machine_authority_change`: изменяются выбор SDK продукта и существующая проверка local tails, без нового carrier/writer/reader, по которому скрипты Planveyor допускают, маршрутизируют, записывают или закрывают работу. Planner переносит только derived N-A ref с canonical SHA-256 из helper readback; semantic core остаётся за Architect.

### Решение по Planner Q2: маршрут проверки и фактические prerequisites

- Обязательный real proof остаётся прежним: при совместно установленных подходящих стабильных SDK 10 и 11 resolver на неизменённом итоговом `global.json` выбирает 10; без подходящего SDK 10 положительная строка выбирает 11. Обе полные офлайн-строки и preparations №1–№3 сохраняются. Отдельный inventory «установлен только SDK 10» не является дополнительным обязательным условием AC1; если он фактически доступен, его можно сохранить как контекст.
- Основной SDK 10 root вправе уже содержать обе ветки. Тогда тот же физический root и тот же launcher используются для SDK 10 row и combined diagnostic, без третьей полной положительной строки, новой setup attempt или повторного запроса того же пути. Если предоставленный SDK 10 root содержит только 10, он закрывает свою положительную строку, но combined diagnostic требует отдельно приватно предоставленного уже подготовленного `MSSQL_DOTNET_BOTH_ROOT`. Это разрешённый diagnostic input, а не подтверждение существования установки и не разрешение её создать.
- Combined diagnostic выполняется из current sibling с итоговыми candidate bytes: один выбранный launcher, фактический `--list-sdks` с допустимыми стабильными 10.0.x и 11.0.x в одном SDK root, затем `--version=10.0.x` при неизменном `global.json` без `sdk.paths` и влияющих launch overrides. Receipt связывает launcher/root/архитектуру, actual inventory, выбранную версию, HEAD и canonical snapshot до/после. Для этих diagnostic commands дополнительный setup не нужен. Копирование SDK, сборка combined tree, symlink layout и изменение установок ролями запрещены.
- `sdk.paths=[root10,root11]` не заменяет combined observation: он доказывает порядок каталогов, а не выбор между SDK внутри одной установки. Это следует из [официальной семантики ordered first-match](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json#paths). Scoped empty-path/no-compatible fixture допустим как отдельный negative resolver proof с честной маркировкой изменённого fixture config; product `global.json` не меняется.
- Согласование этого маршрута — решение Architect. Фактическая доступность roots, их состав и combined observation на этом этапе не подтверждены. По текущему поручению Manager `SDK_COMPAT_*` не переданы; draft использует symbolic `MSSQL_*`, что само по себе не доказывает наличие значений или mapping между именами. Planner сохраняет один явный контракт private selectors; runtime stage принимает только фактически предоставленные и проверенные inputs. Дословный A1 не дополняется выдуманной Owner аттестацией подготовки.

### Независимые шаги и граница исполнения

1. После закрытия semantic Q2 разрешён обычный возврат `Architect response -> Ready for Planner`. Planner обновляет существующий draft: header gate, private inputs, real-resolver cases, Steps, Commands и reroute boundary; повторяет обычные lint/authority/strict bundle gates. Доступность будущих SDK roots не является доказательством этих structural gates и не подменяется ими. Architect не ставит `Ready for Coder` и не пропускает Planner finalize.
2. После такого Planner handoff Coder через обычные `Coder intake -> In progress` вправе выполнить SDK-independent prefix: source/docs/test-fixture изменения только 12 exact targets, чтение и статические проверки, canonical plan/doc checks и `git diff --check`. Этот prefix не вызывает `dotnet`, setup, build, SqlPackage, SQL, установку инструментов или создание SDK tree. Private SDK selectors для самих source edits не требуются.
3. `make test` относится к этому prefix только в самостоятельном подготовленном static envelope: фактические Python 3.12/Darwin, Git и тот же pinned Planveyor runtime; SDK outputs/lookup контролируются существующими synthetic fixtures, без запуска настоящего SDK. Engine `PYBIN` не объявляет проектный Python и не подставляется вместо него. При отсутствии этих собственных prerequisites тест отмечается как не выполненный; source edits и остальные независимые проверки не выдаются за successful test. Planner обязан дать этот envelope отдельно от SDK-dependent `mssql_row`, а не сделать наличие всех SDK roots условием первого редактирования.
4. Перед каждой зависимой командой нужен соответствующий actual prerequisite: до первого `dotnet` — предоставленный launcher/root и объявленный envelope; до setup/build/full row — inputs именно этой положительной строки; до combined/negative diagnostic — их реальные inputs. Missing/ambiguous input останавливает соответствующий шаг до его запуска. Coder фиксирует конкретный недостающий input и выполненный независимый prefix в plan, затем передаёт `Ready for Architect response`; Architect при необходимости формулирует один предметный Owner запрос о приватной передаче готовых prerequisites. Поиск по диску, автоматическая установка, подбор другого launcher и молчаливое создание alias запрещены.
5. Source/fixtures prefix и закрытый Q2 не закрывают real resolver, AC1/AC3, matrix или acceptance. До полного required real proof, двух текущих offline rows и negative-runtime контроля запрещены SQL-approval request и `Ready for Review`; отдельные SQL и concrete commit gates остаются прежними. Значения и наличие SDK paths сейчас не аттестуются. Это обычный bounded developer flow с остановкой на уже объявленном prerequisite, без нового lifecycle override или уменьшения AC.
